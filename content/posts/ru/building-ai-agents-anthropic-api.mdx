Свой поиск работы я веду через инструмент, который сам и написал: jobhunt —
kanban-доска, где каждая карточка — это отклик на вакансию, и к каждому
отклику прикреплён AI-агент. Агент адаптирует CV под вакансию, пишет
сопроводительное письмо и собирает информацию о компании. Бэкенд на FastAPI,
фронтенд на React, Claude через Anthropic API. Этот пост — список вещей,
которые я рассказал бы себе до старта.

## Типизированные инструменты, а не суп из промптов

Первая версия делала то, что делает любая первая версия: запихивала всё в
один промпт. CV, описание вакансии, инструкции, правила форматирования —
стена текста, заканчивающаяся фразой «теперь напиши сопроводительное письмо».
На happy path это работало, везде дальше — деградировало. Длинные вакансии
выталкивали CV из фокуса. Инструкции по форматированию соблюдались примерно
в 80% случаев — вежливый способ сказать «не соблюдались».

Лечение — перестать относиться к модели как к трубе для текста и начать
относиться как к потребителю API, который контролирую я. Каждая способность
агента — это инструмент с JSON-схемой:

```python
TOOLS = [
    {
        "name": "fetch_posting",
        "description": "Return the job posting text for the current application.",
        "input_schema": {"type": "object", "properties": {}},
    },
    {
        "name": "read_base_cv",
        "description": "Return the candidate's base CV as structured JSON.",
        "input_schema": {"type": "object", "properties": {}},
    },
    {
        "name": "save_artifact",
        "description": "Persist a finished artifact for this application.",
        "input_schema": {
            "type": "object",
            "properties": {
                "kind": {"enum": ["cv", "cover_letter", "research"]},
                "content": {"type": "string"},
            },
            "required": ["kind", "content"],
        },
    },
]
```

Цикл оркестрации скучный намеренно: отправляем сообщения, исполняем все
блоки `tool_use`, добавляем `tool_result`, повторяем, пока модель не
перестанет спрашивать. Модель решает, *на что* смотреть; мой код решает,
*что эти данные собой представляют*. Системные промпты ужались до короткого
описания текущей задачи, а качество вывода перестало зависеть от того,
«вспомнила» ли модель что-то из стены в 6k токенов.

## SSE — потому что данные текут в одну сторону

Агент стримит токены в UI. Рефлекторный выбор — WebSockets; я взял
Server-Sent Events и ни разу не пожалел.

Аргументация прозаичная. Стриминг токенов однонаправленный: клиент шлёт один
запрос — «запусти агента» — а сервер пушит чанки. Дуплексный канал здесь не
даёт ничего, а стоит вполне конкретных вещей: connection upgrade, который не
любят корпоративные прокси, самописная логика реконнекта, heartbeat'ы. SSE —
это обычный HTTP. Он проходит через любой прокси, переиспользует обычный
auth-middleware, а браузер сам переподключается через `Last-Event-ID`.

```ts
const es = new EventSource(`/api/applications/${id}/agent/stream`);
es.onmessage = (e) => {
  const chunk = JSON.parse(e.data) as AgentChunk;
  if (chunk.type === 'token') appendToken(chunk.text);
  if (chunk.type === 'tool') showToolBadge(chunk.name);
  if (chunk.type === 'done') es.close();
};
```

Деталь, которую стоит украсть: стримьте не только токены, но и события
инструментов. Надпись `→ fetch_posting` в UI, пока агент работает,
превращает 40-секундное ожидание из «оно сломалось?» в индикатор прогресса,
доставшийся бесплатно.

## Долгие вызовы агента против вашей базы данных

Запуск агента с двумя-тремя раундами инструментов занимает 30–90 секунд. На
синхронном стеке каждый запуск держит воркера всё это окно; несколько
параллельных запусков — и API голодает. Поэтому jobhunt асинхронный от края
до края — FastAPI плюс SQLAlchemy 2.0 с async-сессиями.

Неочевидная часть: не держите одну сессию на весь запуск. Моя первая
реализация открывала сессию на старте агента и коммитила в конце. Итог —
соединения, висящие в idle-in-transaction минутами. Сессиям место внутри
обработчиков инструментов: открыли поздно, закрыли рано.

```python
async def fetch_posting(app_id: int) -> str:
    async with Session() as session:
        row = await session.get(Application, app_id)
        return row.posting_text
```

Сам запуск агента не владеет ни одним соединением. Каждый инструмент
одалживает его на миллисекунды и возвращает обратно.

## Контекст — на отклик, а не на чат

Поначалу был один глобальный чат с агентом. Он постоянно путал вакансии:
«эта позиция» могла означать любую из дюжины, и артефакты не раз ложились не
на ту карточку.

Рабочая модель: каждая карточка отклика — отдельный контекст агента.
Системный промпт собирается обычной функцией из строки отклика в базе:
вакансия, базовое CV, ранее сгенерированные артефакты, прошлые сообщения по
этой карточке. Сборка контекста — это код, а не вайбы. Агенту никогда не
приходится угадывать, о какой вакансии речь, потому что он видел ровно одну.

## Что не сработало

- **Давать модели писать в базу напрямую.** Ранний инструмент `save_cv`
  срабатывал посреди рассуждений и сохранял полуфабрикаты. Теперь агент
  возвращает артефакты и явно помечает их финальными; что сохранять — решает
  приложение.
- **Один мега-агент.** Единственный агент, делающий адаптацию CV, письма и
  ресёрч, требовал противоречивого промпта. Три сфокусированных агента с
  общими сборщиками контекста по отдельности глупее, а в сумме лучше.
- **Формат через прозу.** «Ответь валидным JSON» работает, пока не
  перестаёт. Если у вывода есть структура — делайте tool call со схемой: API
  её валидирует, и режим отказа превращается из бага парсинга в ошибку.
- **Слепые ретраи.** Повтор упавшего запуска без ключей идемпотентности
  плодил дубли сопроводительных писем. Теперь у каждого запуска есть id;
  артефакты делают upsert по нему.

## Если бы я начинал заново

Архитектуру я бы оставил: типизированные инструменты, SSE, async-сессии,
контекст на отклик. Пропустил бы каждый шаг, где доверял прозе в промпте
работу, которую должна делать схема. Самая полезная привычка — относиться к
агенту как к ненадёжному джуну с феноменальной памятью: давать ему маленькие,
хорошо типизированные интерфейсы и проверять всё, что он приносит обратно.
