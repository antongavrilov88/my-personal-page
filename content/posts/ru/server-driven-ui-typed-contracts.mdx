На моей текущей работе backend-driven UI (BDUI) обслуживает примерно 27–30%
продуктовых поверхностей. Эта цифра есть в моём CV; интересно другое —
*почему* архитектура её заслуживает. Короткий ответ: не трюк с рендерингом, а
типизированные контракты. Пост остаётся на публичном уровне детализации:
паттерны общие, никаких проприетарных внутренностей.

## Проблема трёх релизных поездов

Фича, затрагивающая web, iOS и Android, релизится трижды. Web деплоится
ежедневно. iOS проходит ревью App Store. Android раскатывается поэтапно.
Фича «готова», когда приходит самый медленный поезд — обычно через недели
после того, как код дописан. Дальше начинается длинный хвост: старые версии
приложений живут в дикой природе месяцами, так что каждая клиентская фича —
это вечное обязательство по совместимости.

Умножьте это на десятки продуктовых команд, выкатывающих фичи еженедельно, —
и релизный календарь становится настоящей архитектурой компании.

Server-driven UI бьёт по самой связке: *описание* экрана переезжает на
бэкенд. Клиенты один раз выкатывают рендерер. После этого изменение схемы
доезжает до web, iOS и Android в один и тот же момент, без релиза приложения
на критическом пути.

## Схема на входе, компоненты на выходе

Форму системы легко сформулировать:

- бэкенд собирает типизированный UI-контракт — валидируемое JSON-дерево
  узлов — из фиче-флагов, экспериментов и правил раскладки;
- каждая платформа держит рендерер, который сопоставляет узлам схемы
  нативные компоненты: TypeScript/React на web, нативные view на мобильных.

Рендерер знает *примитивы* — текст, список, карточку, действие — и ничего не
знает о фичах. Это незнание и есть суть; мы к нему вернёмся.

Наивная версия звучит как «JSON описывает UI» — и наивная версия
проваливается. JSON описывает happy path. А реальные экраны заметную долю
жизни грузятся, падают и стоят пустыми.

## Типы, которые делают плохие состояния непропускаемыми

Самое высокорычажное решение в BDUI-системе — то, что контракт *отказывается*
выражать. Вот паттерн, сведённый к скелету:

```ts
type Slot<T> =
  | { state: 'loading' }
  | { state: 'error'; message: TextNode; retry?: Action }
  | { state: 'empty'; placeholder: TextNode }
  | { state: 'ready'; data: T };

interface ProductList {
  kind: 'product-list';
  header: TextNode;
  items: Slot<ProductCard[]>;
}
```

`items` — это не массив. Это discriminated union, и у рендерера нет способа
добраться до данных, минуя `switch` по `state`. Добавьте проверку
исчерпываемости — и компилятор закрывает последний выход:

```ts
function renderSlot<T>(slot: Slot<T>, ready: (data: T) => UINode): UINode {
  switch (slot.state) {
    case 'loading': return spinner();
    case 'error':   return errorView(slot.message, slot.retry);
    case 'empty':   return slot.placeholder;
    case 'ready':   return ready(slot.data);
    default:        return assertNever(slot); // новое состояние? сборка упадёт
  }
}
```

Культурный эффект больше технического. Загрузка, ошибка и пустота перестают
быть «полировкой, которую доделаем после дедлайна» — экран, который их не
определил, *не компилируется*. Никому не нужно помнить; никому не нужно
ловить это на ревью. Чек-лист — это система типов.

## Композиция вместо конфигурации

Словарь SDUI растёт двумя путями, и выживает только один.

Путь конфигурации: узел `List` обрастает опциями — `compactMode`,
`showDividers`, `badgeStyle`, `headerVariant`. Каждый флаг удваивает
пространство состояний; N флагов — это 2^N комбинаций, большинство
непротестированы, часть бессмысленна. Каждая платформа реализует флаги чуть
по-своему, и матрица гниёт.

Путь композиции: узлы маленькие и *вкладываются*. Список принимает дочерние
узлы; карточка принимает дочерние узлы; бейдж — это узел, который ставишь
куда нужно. Рендерер разрешает дерево. Когда продуктовая команда придумывает
новый экран, она составляет существующие примитивы в новую форму — и рендерер
выкатывается с **нулём изменений**, потому что он о фичах и не знал.

Конфигурация просит у платформенной команды разрешения. Композиция — нет.
В этой разнице — большая часть выигрыша в скорости.

## Что дрейфует, когда контракты не типизированы

Я видел нетипизированную версию этого кино, и распад там предсказуем:

- **Опциональные поля расходятся по платформам.** Web считает отсутствующее
  поле пустым, одна мобильная платформа прячет блок, другая рисует пустоту.
  Три оправданных прочтения одного JSON — три разных экрана.
- **Состояния ошибок умирают первыми.** Ничто не заставляет их существовать,
  и они тихо превращаются в вечные спиннеры, а затем в пустые экраны.
- **Версионирование становится археологией.** Какие поля понимают клиенты
  годичной давности? Без типизированных контрактов ответ — племенное знание.
  С ними — механика: версионированные схемы и явный fallback-узел, который
  старые рендереры показывают для незнакомых типов.
- **Паритет разъедается молча.** С единой типизированной схемой визуальное
  или поведенческое расхождение платформ — это баг контракта, на который
  можно показать пальцем, а не спор о per-platform реализации.

## Сколько это стоит

Секция честности. Рендерер — полноценный продукт со своим роадмапом, тестами
и дежурствами. Отладка пересекает сетевую границу: вопрос «почему этот экран
выглядит не так» теперь начинается с JSON-пейлоада. А проектирование схемы —
это проектирование API, с тем же весом ревью и той же ценой ошибок: неудачная
форма узла, однажды уехав на клиенты, остаётся навсегда.

Если у вас одна платформа — пропустите всё это. Архитектура окупается там,
где узким местом становятся три релизных поезда и длинный хвост старых версий
приложения, — ровно в той точке, где типизированные контракты перестают быть
приятным бонусом и становятся несущей стеной.
